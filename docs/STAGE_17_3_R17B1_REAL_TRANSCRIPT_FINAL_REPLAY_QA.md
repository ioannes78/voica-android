## R17A input evidence

R17A real-device ①–⑧ all passed as *single-run feasibility checks* on LiteRT-LM 0.18.0,
Gemma 4 E2B-IT candidate r1, CPU. Relevant evidence:

- 8K context completed 5,046 **estimated** prompt tokens; 16K completed 12,534 estimated tokens,
  but 16K took about 250 seconds and 3.14 GiB peak PSS.
- The **synthetic fact ID** cap increased from 8/16 to 16/16 when QA item capacity and the
  matching max-items prompt instruction were raised; this was not real semantic accuracy.
- A 2,048 output-token cap was accepted by the runtime; not proof output used >1,024 actual tokens.
- Small-input 8K increased peak PSS vs 4K with no gain in 16/16 fact-ID coverage.

Do not promote product defaults solely based on these observations.

## R17B-1 controlled experiment

Use the existing build-time Stage 17.3 diagnostic TXT generated by the user's actual completed
long-transcript summary. It contains **FINAL INPUT** (compact, validated MAP/REDUCE facts)
and **FINAL OUTPUT** (the saved baseline JSON) plus earlier PLAN/MAP/REDUCE text.

The QA-only Stage 17 P1 screen adds a manual Android document picker. The user chooses a
WENZHI-Stage17.3-LongSummary-Diagnostic-*.txt; the app checks the diagnostic format/version,
extracts the exact frozen FINAL prompt and baseline result, estimates the prompt budget,
enumerates visible Sxxxxx Evidence refs, hashes the prompt and refuses oversized imports.

The real file may contain private transcript-derived data. Nothing is sent to the Internet;
it is read by the app through the user's explicit document selection. Model inference remains
local CPU, uses the existing AppLocalLlmRuntime resource gate and one native request at a time.

| Candidate | Context | FINAL JSON schema | Output tokens | Isolated comparison |
| --- | ---: | --- | ---: | --- |
| Original baseline | 4K | production 4 sections × 2 items | 1024 | Prior real user run in diagnostic TXT |
| B1 | 4K | QA 4 sections × 4 items | 1024 | Relax per-section item bound only |
| B2 | 8K | Same QA 4×4 | 1024 | Larger context only |
| B3 | 8K | Same QA 4×4 | 2048 | Larger output reserve/cap only |

The **prompt bytes are identical** in B1/B2/B3 (record its SHA-256). QA schema is derived
from the current real production schema, changing *only* the nested per-section items.maxItems
from 2 to 4. The shared production response-format function is never edited.

All three requests are budget gated before native initialization:
`conservativePromptEstimate + outputCap + 192 template + 256 safety <= maxNumTokens`.
Abort the candidate if it cannot fit. Do **not truncate the source**. 4K candidates use the
same 2,528 estimated maximum as existing production; B2/B3 preserve source even if longer
context is available.

## How to run

1. Install the R17B QA APK by **cover install**. Do not clear app data.
2. Find the existing text report for golden sample `EHBZKFZH6GIZG.m4a` in Downloads/WENZHI,
   produced by a **completed** Stage 17.3 quality-diagnostic Long Summary (R16.6 or later).
   If unavailable, generate a new Long Summary in the QA APK before the replay.
3. Open the existing **Stage 17 P1 · Local LLM Runtime** screen, expand
   **R17B-1 · 真实转写 FINAL 同源对照** and select the TXT.
4. Verify the displayed frozen prompt estimate, NODE count and SHA.
5. Manually run B1 → B2 → B3 **one by one**; stop on OOM, native crash, process restart,
   RELEASE_UNCONFIRMED or unreasonably high memory consumption.
6. Choose **保存原始与新版本对照报告 TXT** and send it for source-by-source QA review.
   The report includes user transcript-derived text: disclose only voluntarily.

## Measurement and validity

- Runtime: initialization, TTFE, generation time, peak/after-close PSS, backend, fallback.
- Schema: real `SummaryResultCodec.decode`, section/item counts, valid refs,
  TRANSCRIPT_STATED vs synthesis counts and distinct S refs.
- Compare content manually against original MAP/REDUCE and raw transcript:
  verify *quantitative figures, proper names, cases, negation, risks, conclusions, uncertainty*.
- Check every `evidenceRefs` value **against the evidence text**, not just its existence.
  Valid Sxxxxx membership does not establish fact support; empty refs under AI_SYNTHESIS
  are not equivalent to transcript-grounded statements.
- Count true source-backed facts, novel hallucinations, duplication and inaccuracies across
  versions. Keep a fixed human-graded fact rubric, not an automated "100%" label.
- The imported FINAL input contains only information survived MAP/REDUCE; no FINAL replay can
  recover facts already lost upstream. Inspect original PLAN/MAP/REDUCE diagnostic as R17B-2.
- The original baseline can differ due to stochastic sampling; single-run outcomes are
  exploratory, and repeated frozen-input runs are needed to estimate variability.
