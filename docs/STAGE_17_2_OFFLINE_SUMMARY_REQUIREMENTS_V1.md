## 1. Goal

Stage 17.2 adds the first product-facing fully offline transcript summary path for WENZHI.

The required product path is:

```text
Current Effective Transcription
  -> StructuredTranscriptInput
  -> Offline Summary Prompt
  -> Direct Input Budget Gate
  -> AppLocalLlmRuntime
  -> Gemma 4 E2B through LiteRT-LM
  -> strict structured-result validation
  -> optional bounded one-time local repair
  -> validated AiSummary result
  -> evidence mapping to canonical transcript/audio lineage
  -> existing summary/version/search/export UI and persistence
```

This stage is intentionally a **direct-summary V1**. Long-transcript map/reduce, retrieval, hierarchical summarization and checkpointed multi-pass pipelines belong to Stage 17.3.

---

## 2. Hard architecture requirements

1. The product summary path MUST reuse the P1 application-facing runtime boundary: `AppLocalLlmRuntime.generate(...)`.
2. Summary code MUST NOT create or own a second LiteRT-LM `Engine`, `Conversation`, native runtime or competing local-LLM owner.
3. P1 runtime resource arbitration, backend resolution, cancellation and model-use lease behavior remain authoritative.
4. Product summary requests MUST use `LocalLlmBackendPolicy.AUTO`.
5. Summary code MUST NOT implement an independent GPU/CPU fallback policy.
6. The P1 safe-fallback rule remains unchanged: pre-generation recoverable GPU failures may fall back safely; generation-time failure, OOM and uncertain native state MUST NOT be blindly retried on CPU.
7. Local LLM work remains isolated from recording, BLE, playback and ASR critical paths.
8. No cloud inference fallback is permitted.

## 5. Input truth and lineage

The only semantic input for one generation is a single frozen snapshot of the **Current Effective Transcription** resolved at task start.

The snapshot MUST preserve enough lineage to identify the exact input version used by the generation, including where available:

- `recordingId`
- `transcriptionId`
- `transcriptionRevisionId`
- input content digest
- alignment ID
- canonical asset ID
- canonical audio SHA-256
- canonical profile ID

Once generation starts, the task MUST NOT silently switch to a newer transcription/revision.

Manual revisions that cannot be mapped reliably to canonical audio MAY participate in semantic summarization but MUST be marked as not evidence-addressable. They MUST NOT receive fabricated sample positions.

---

## 6. Structured transcript input

WENZHI owns the evidence coordinate system.

Each transcript unit supplied to the model MUST use a deterministic application-generated evidence reference, for example:

```text
[S00001][说话人 1]
今天确认第一版周五发布。

[S00002][说话人 2]
测试需要在周四结束。
```

Units without a reliable evidence anchor MUST be distinguishable, for example with a `NO_EVIDENCE` marker.

The LLM:

- MAY reference only evidence IDs supplied in the frozen input;
- MUST NOT invent evidence IDs;
- MUST NOT invent timestamps;
- MUST NOT invent sample indices;
- MUST NOT determine playback seek positions.

Application code maps accepted evidence IDs back to canonical transcript/audio coordinates.

Principle: **LLM 负责语义，WENZHI 负责时间坐标。**

---

## 7. Prompt/output contract

Stage 17.2 uses an offline-summary-specific prompt version namespace.

Initial frozen prompt version:

`OFFLINE_SUMMARY_PROMPT_VERSION = 170201`

The result schema remains versioned independently; initial expected result schema is `1`.

The prompt MUST require:

- Simplified Chinese by default;
- JSON-only structured output;
- no Markdown code fence around the payload;
- allowed `contentType`/summary section structure defined by the current summary result contract;
- epistemic status rules;
- evidence reference rules;
- no unsupported factual invention;
- no timestamp/sample-index generation.

Raw model output MUST NOT be persisted as a completed summary merely because text was produced.

---

## 8. Direct input budget

Stage 17.2 MUST perform a direct-input budget preflight before starting native model initialization.

Budgeting MUST account for:

- prompt overhead;
- structured transcript content;
- evidence markers;
- output reserve;
- safety reserve.

If a reliable LiteRT-LM tokenizer/token-count API is available and suitable for production, use it. Otherwise use a deterministic conservative estimator that is testable and calibrated with the validated Gemma runtime.

The app MUST NOT use an unverified theoretical model context window as the sole product limit.

If the input exceeds the validated direct-summary budget:

- return `INPUT_TOO_LARGE_FOR_DIRECT_SUMMARY`;
- do not initialize the model;
- do not silently truncate;
- do not summarize only a prefix;
- do not auto-map/reduce in Stage 17.2.

Long transcript intelligence is deferred to Stage 17.3.

---

## 9. Local LLM generation preset

The P0 baseline preset remains a runtime regression reference, not the permanent product summary preset.

Stage 17.2 MUST introduce a separately named offline-summary generation preset while staying within the already validated LiteRT-LM operating envelope until real-device evidence supports tuning.

Initial tuning principle: **stabilize structured output before optimizing writing style.**

Do not simultaneously make large unvalidated changes to max tokens, top-k, top-p, temperature and speculative decoding.

---

## 10. Validation and bounded repair

The first model response MUST be decoded through the existing strict summary result contract/codec.

If it is valid, continue normally.

If it is invalid and classified as repairable, Stage 17.2 MAY perform exactly one local repair generation using:

- the same frozen transcript snapshot;
- the invalid first output;
- the validation error;
- the exact allowed evidence-ref set;
- the exact output schema.

The repair path MUST:

- use `AppLocalLlmRuntime`;
- use AUTO backend policy;
- remain fully offline;
- not switch models;
- not mutate the transcript snapshot;
- not expand the allowed evidence set;
- not perform a second repair;
- re-run full strict validation afterward.

Application code MUST NOT convert arbitrary invalid model text into a fake valid result through regex/JSON patching that bypasses the schema contract.

If the repair still fails, persist a failed generation state and do not publish partial result content.

---

## 11. Evidence validation

Every evidence reference in a successful result MUST exist in the frozen input allowlist.

Unknown evidence refs MUST cause validation failure.

Successful evidence persistence MUST map from the application-owned source reference to existing canonical evidence fields, including where available:

- summary item ID;
- source ref;
- source kind;
- source ID;
- start sample index;
- end sample index exclusive;
- speaker ID;
- assignment quality.

The LLM is never the source of canonical sample positions.

---

## 12. Persistence and version lifecycle

Stage 17.2 MUST reuse the existing summary persistence/version model and Stage 12C content-version lifecycle.

Room schema MUST remain **version 16** for this stage.

No new table/column/migration is authorized by this requirement set.

Each generation creates a new immutable summary identity. Regeneration MUST NOT overwrite an older summary row.

The generation lifecycle is:

```text
CREATED
  -> PREPARING
  -> ANALYZING
  -> VALIDATING
  -> COMPLETED
```

Terminal abnormal states:

```text
FAILED
CANCELLED
INTERRUPTED
```

Stage 17.2 does not introduce Stage 17.3 states such as `PLANNING`, `MAPPING` or `REDUCING`.

A successful completion MUST persist validated structured content, display text, evidence rows, completion metadata and lineage consistently before the result is exposed as completed.

Existing current/candidate behavior remains authoritative:

- first summary may become current;
- later regeneration is a new candidate/version;
- user selection controls promotion to current;
- historical versions remain available.

---

## 13. Model identity persistence

A locally generated summary MUST preserve a traceable model identity containing enough information to recover:

- model ID;
- model version/revision;
- artifact identity/SHA;
- LiteRT-LM runtime version.

User-facing UI may display a concise label such as `Gemma 4 E2B · 本地`, but diagnostics/lineage must remain precise.

Historical summaries MUST retain their original provider/model lineage and MUST NOT be relabeled as local.

---

## 14. Coordinator and ownership

Stage 17.2 MUST introduce an application-level offline summary coordinator rather than putting generation ownership in Compose, an Activity, or a transient UI scope.

The coordinator MUST:

- resolve and freeze the effective transcript once at start;
- prevent duplicate summary launches for the same active task;
- call `AppLocalLlmRuntime` only through the formal product boundary;
- surface P1 runtime BUSY/resource/model failures as product-level summary failures;
- own the coroutine job used for cancellation;
- release all task ownership on success/failure/cancellation;
- keep UI state observational rather than engine-owning.

P1 remains the global local-LLM single-owner boundary even if the summary coordinator also performs feature-level duplicate suppression.

---

## 15. Interaction with recording/ASR and other heavy work

Summary generation MUST NOT stop, replace, degrade or steal ownership from recording/realtime/ASR critical tasks.

Before starting a summary, the product layer MUST block or defer when an incompatible critical task is active rather than forcing the critical task to stop.

Recording truth and ASR truth take priority over summary convenience.

---

## 16. Cancellation, navigation and process restart

User cancellation MUST cancel the coordinator job and flow through coroutine cancellation into the P1 runtime cleanup path.

Cancellation MUST NOT persist partial structured results as completed.

Navigation away from the summary page, tab changes and Activity recreation MUST NOT automatically cancel a running summary while the application process remains alive.

Stage 17.2 does not promise survival across process death. On startup, any non-terminal summary left in `CREATED`, `PREPARING`, `ANALYZING` or `VALIDATING` MUST be reconciled to `INTERRUPTED` rather than silently resumed or duplicated.

A user may explicitly start a new generation afterward.

---

## 17. Product UI requirements

Stage 17.2 integrates into the existing summary product surface rather than creating a separate summary app/page architecture.

Required states include:

- no summary / generate offline summary;
- local model missing / route to local-model management;
- preparing;
- analyzing;
- validating;
- cancel action;
- failed with product-level error text;
- completed summary;
- regenerate;
- candidate/current handling.

The UI MUST NOT expose raw JNI stack traces or fake percentage progress when no real progress metric exists.

Existing summary editing, evidence interaction, search, copy/share and export behavior should continue to work for completed local summaries.

---

## 18. Historical compatibility

Stage 17.2 MUST preserve historical online/provider-generated summaries.

Historical content:

- is not migrated to local;
- is not deleted;
- is not automatically regenerated;
- retains its original provider/model lineage;
- retains evidence/history/revision behavior;
- remains readable by the existing schema/result compatibility path.

Local and historical summaries coexist in the same product version history.

- `MODEL_NOT_INSTALLED`

- `INPUT_TOO_LARGE_FOR_DIRECT_SUMMARY`
- `RESOURCE_BLOCKED`
- `RUNTIME_BUSY`
- `ENGINE_INIT_FAILED`
- `GENERATION_FAILED`
- `GENERATION_CANCELLED`

- `REPAIR_FAILED`

## 22. Acceptance gates

Stage 17.2 cannot close until all applicable gates pass:

1. Architecture: one P1 local-LLM owner, AUTO backend, no parallel Engine.
2. Offline: airplane-mode generation succeeds, no cloud fallback.
3. Data: Room v16 unchanged, immutable summary/version lifecycle correct.
4. Evidence: only frozen allowlisted evidence, no LLM-generated time coordinates.
5. Reliability: cancellation, invalid-output rejection, one bounded repair, interrupted recovery and over-budget rejection.
6. Compatibility: historical summaries, revisions, search/export/evidence/playback and ASR/diarization baselines remain intact.
7. Production-like build: releaseQa, minification/resource shrink, R8/JNI verification and automated CI pass.
8. Real-device QA: performed one test item at a time; untriggerable fault/thermal paths must be reported as not covered rather than falsely marked PASS.
