# Stage 13C C3 — CAM++ / Native Execution Path Audit

Status: **AUDIT COMPLETE — no safe high-value API-level optimization identified**.

This is a Stage 13C intermediate gate. It is not a Freeze/final candidate.

## Inputs

C0/C1/C2 real-device profiling established two relevant facts:

1. sherpa `NATIVE_DIARIZATION` remains the dominant cost and varies materially between otherwise comparable runs.
2. the app's additional CAM++ anchor extraction remains roughly 7–10% of wall time, but C2 proved that exact-range reuse does not occur in the tested production workload.

C2 has therefore been removed rather than broadened into fuzzy/semantic cache reuse.

## Runtime/API verified

The audit was performed against the sherpa-onnx **v1.13.8** API used by Voica.

### SpeakerEmbeddingExtractor

The Kotlin/JNI public execution path exposes single-stream operations:

- create an extractor stream
- accept waveform into that stream
- mark input finished
- verify readiness
- compute one embedding from that stream
- release the stream

The public API does not expose a true batch-embedding call for multiple independent anchor ranges.

Independent anchor ranges require independent stream state. Reusing a stream after `inputFinished()`/`compute()` as if it were a resettable batch slot is not an established public contract and is therefore not adopted.

### OfflineSpeakerDiarization

The public `OfflineSpeakerDiarization.process(samples)` path returns diarization segments. It does not expose the internal CAM++ speaker embeddings/vectors generated by the native diarization pipeline.

Therefore Voica cannot safely consume the native pipeline's internal embeddings for cross-window stitching without changing runtime/native integration boundaries.

## Options rejected in C3

### Synthetic batching

Rejected. There is no verified v1.13.8 batch embedding API. Looping single calls behind a method named "batch" would not remove the underlying compute or stream lifecycle and would misrepresent the optimization.

### Shared-stream reuse

Rejected. Independent anchor audio requires isolated extractor state and the public API does not define a reset/recycle contract after a completed embedding.

### Concurrent embedding calls on one extractor

Rejected for the current stage. Thread safety for concurrent stream compute on one extractor has not been established as a supported contract, and introducing concurrency would also compete with the already CPU-heavy native diarization path.

### Multiple extractor instances for parallel CAM++

Not adopted. It would duplicate native sessions/model working state, increase RAM/thermal pressure, and has no evidence yet that wall-time gain exceeds contention on the target Android device.

### Reusing OfflineSpeakerDiarization internal CAM++ vectors

Not possible through the current public API. Doing so would require a deeper native/runtime change and is outside a low-risk C3 optimization.

## Minor allocation opportunity

The current anchor path copies each selected anchor range from the window `ShortArray`, then the Sherpa wrapper converts that new array to a `FloatArray` before native compute.

An offset/range-aware embedding API could remove the intermediate `ShortArray.copyOfRange` allocation. This would not remove CAM++ inference, stream creation, feature extraction, or compute. Given measured anchor cost of roughly 11–14 seconds per ~6-minute sample, this allocation-only change is not treated as a material performance solution without dedicated evidence.

C3 therefore does not add this API churn solely for speculative micro-optimization.

## C3 decision

Close C3 without a production algorithm/runtime change.

Retain:

- C0 production profiling
- accepted C1 lineage-safe VAD reuse
- current Pyannote Segmentation 3.0 INT8 + CAM++ + native clustering chain
- existing stitching/alignment semantics
- Room v11
- current production model channel

Remove/reject:

- C2 exact-range anchor cache
- speculative fuzzy cache
- invented batching
- unverified stream reuse/concurrency

## Why C4 is next

The remaining measured cost is dominated by native diarization. The rapid-turn real-device sample processed 6,473,968 window samples for 5,513,968 unique samples: 960,000 samples of duplicate window coverage, a processing factor of approximately 1.174x. The normal-conversation sample duplicated 160,000 samples (~1.029x), while the single-speaker control duplicated none.

This does not prove that native cost scales linearly with overlap, but it provides a measurable C4 target with materially higher potential leverage than exact anchor-range caching.

## C4 guardrails

C4 must remain data-gated:

- measure existing window/overlap duplication before changing semantics
- prefer eliminating redundant native work without changing canonical timeline truth
- preserve speaker continuity/stitching correctness across boundaries
- do not silently reduce overlap or alter clustering thresholds as a shortcut
- A/B any window/overlap change on the same recordings
- retain DER/JER only for datasets with ground truth
- any core runtime/model/clustering redesign requires a separate confirmation gate
